## 2. P05 原始任务与实际实现

研究问题写在设计首段：给定一张已校验的图、一个本地单 Skill 快照，以及可选的分析者绑定原件，每条能力或图关系的依据能否回到当前材料。

`build_index(graph, root, binding_file=None)` 先调用 `validate_graph`。然后用 P03 的 `scan` 枚举快照。普通文件的 SHA-256 取自解码和换行转换之前的原始字节。登记文件在单独的 256 KiB 预算内只为哈希读取，不解释内容。SCS 里写下的路径不会被拿去打开。

每个主张在整份当前材料上重放 P03 提取。完整主张的规范 JSON 相同，且出现次数相同，才按重放顺序配对。次数不符则该键的全部分配都不建立 witness。Python 调用在配对成功时附带 `ast.Call` 的 UTF-8 字节列。绑定文件必须整份规范 JSON 等于图内绑定表，再记录每个对象的字符区间；不一致则整表缺证，格式非法则抛出 `ValueError`。

输出是 p05.1。`by_file`、`by_capability`、`by_target` 构成双向索引。目标状态为 `verified`、`partial` 或 `missing`。全部目标都是 `verified` 时 `mapping_status` 为 `verified`，否则为 `incomplete`。`scs_status` 和 `runtime_observation` 原样保留。CLI：全部可追溯退出 0，合法缺证打印 JSON 并退出 1，输入或契约错误退出 2。

实现提交没有加入版本配对、重命名相似度、跨技能 handoff、策略搜索或风险标签。`src/` 中没有这些算法。

## 4. 算法正确性分析

配对键是整条主张的规范 JSON，其中包含证据路径、行号、片段、方法和置信度。因此两个只是文本相同、行号不同的 `Accept text.` 不会共用一个 witness。次数必须与重放结果相同：文件里有两次完全相同的调用、图里只留一次时，留下来的那次也是 `missing`。这比“至少找到一处”更严，并且和设计里的“出现次数一致”相符。

`possible` 没有被收成行为确认。边的 `status` 表示来源是否都回到了当前字节；`uncertainty` 仍是 P04 的 `certainty`。样例中唯一的 `reads` 边是 `/edges/19`，两端 witness 的行号都是 17，文件都是 `SKILL.md`，状态 `verified`，不确定性 `possible`。`scripts/format.py` 的调用 witness 为第 2 行、列 `[11,24)`、源码 `value.strip()`。该文件 SHA-256 为 `92c1fc270f99ffc096f3bdda44e5ab4634f468e4aac18ef2cd98beffd77bf931`，与对原始字节独立计算的结果相同，也与验收记录相同。

哈希覆盖整个默认流。空资源 `resources/empty.txt` 的区间是 `[0,0)`，哈希是空字节串的 SHA-256。超过 32 KiB 的登记文件没有 witness，扫描诊断为 `inventory_hash_limit`。内容不被解码，也不进入 `by_file`。

同一图对字节相同的另一个目录得到 `verified`，对 `Return URL.` 得到 `incomplete`。身份依据是当前字节能否重放出主张，不是目录名或 frontmatter 里的 `name`。设计写明指针只在当前快照内有意义，也写明今天的哈希不能证明历史字节。这个结果符合契约。

含写文件调用的样本在 `build_index` 之后没有创建标记文件。分析只使用 `scan`、哈希和 `ast.parse`。

`validate_graph` 仍是 P04 的投影自洽检查。P05 在此之后才对照磁盘。内部自洽的图，只要快照已经改变，仍会得到 `missing`。尾随空格和 YAML 键序变化都会使片段不再匹配。P05 把它们保持为文本证据失败，没有写成“语义上仍是同一个端口”。

## 5. 差分算法专项分析

本节的版本差分清单不适用于 P05。设计没有 V1/V2、没有 ADDED/DELETED/MODIFIED/RENAMED/UNCHANGED，也没有相似度阈值。不把这些缺失记为功能遗漏。

与证据映射对应的性质如下。

| 性质 | 结果 |
|---|---|
| 同一快照再索引 | `Accept text.` 的图对同一目录为 `verified`。两次 `build_index` 相等，且不修改调用方图 |
| 确定性 | 上项相等。样例重建与全量测试可重复 |
| 目标完整性 | 图中的每条边都进入 `by_target.edges`。次数、位置或片段不符时为 `missing`/`partial`，不是丢弃目标 |
| 方向 | 不适用。没有版本对，也就没有 V2→V1 的反向差分 |
| 匹配唯一性 | 相同内容的 `other.py` 不能填上已被改写的 `code.py`。重命名和移动后，旧路径缺证，新路径不会自动接上 |
| 证据可追溯 | witness 含命名空间、相对路径、哈希、行号或字符区间、片段。未验证目标另存 `unverified_location` |
| 不确定性 | `partial` 表示必要来源只回来一部分。`possible` 保持原值。扫描失败留在 `scan_diagnostics` |

新增文件、纯换行和重命名的实测含义：

- 在已验证快照旁增加 `note.txt` 后，`mapping_status` 仍为 `verified`，`by_file` 没有这个新文件。p05.1 证明的是图中已有目标还能对上当前字节，不是目录清单没有变化。
- 只把 `LF` 改成 `CRLF` 时，主张仍可验证，哈希变成 CRLF 原始字节的哈希。换行被保留为字节差异，没有被当成“文件不存在”。
- `code.py` 改名为 `moved.py`，或移入 `scripts/` 后，旧路径 witness 为空，索引状态为 `incomplete`。没有按内容哈希推断重命名。

这些都是证据契约的结果。后续差分如果需要“新增文件”或“重命名”，必须另做算法，不能从本索引的缺席推出“没有新增”。

## 6. 参考论文与实现一致性

KnotScryer §III-B 把输入、输出、效果、操作、上下文和信任边界做成带证据的主张。已获取正文要求证据支撑 handoff，并反对用空证据建立高置信边。它没有规定 SHA-256、整文件重放、AST 列号或双向索引。§III-C 的跨技能四条件不属于本阶段。RogueOne 的程序级污点差分没有出现在 P05 的设计和代码里。

| 对象 | 归类 |
|---|---|
| 主张上的路径、片段、方法、置信度必须能回到材料 | Necessary Adaptation。字段沿用 P03 已实现的 SCS 证据，重放规则是本项目为了可回溯而加的 |
| 字节哈希、BOM/换行顺序、AST 列、绑定字符区间、双向索引、三值状态 | Original Extension。设计写明这些不是论文算法 |
| 跨技能 Evidenced 条件、版本间安全差分 | 未实现，且不应在本阶段实现 |

验收记录没有把文件哈希写成 RogueOne 差分，也没有把 `verified` 写成论文中的运行时证据。这个边界成立。

## 7. 前置模块与接口分析

`1fc4158` 对冻结模块的改动是可选钩子。`scan` 的 `on_bytes` 默认不启用，因此 `extract` 不会为登记文件额外读字节。`python` 的 `on_call` 默认不启用，提取出的主张结构不变。全量测试仍包含 `test_scs.py`、`test_p03_review.py`、`test_skill_reader.py` 和 `test_graph.py`。

P05 消费的是通过 `validate_graph` 的整张图，以及其中内嵌的 p03.2。位置指针仍只解释当前这张图。P04 的接收者标签如果与源码空白不一致，P05 验证的是调用主张本身，不会单独重算接收者标签。这是前置表现，不是 P05 新引入的匹配错误。

Setext、`partial` 和 `failed` 的含义没有被改写。样例在 P03 意义下仍是 `partial`，同时证据映射可以是 `verified`。

绑定路径有自己的根检查、重解析点检查、普通文件和单链接检查，以及 1 MiB 上限。它不被 SCS 里的路径驱动。

## 8. 科研科学性评价

算法由“当前字节能否支持已经记录的证据指针”驱动。测试使用合成快照和临时目录，没有按样本名或冻结评价标签分支。`verified` 与 `scs_status`、`runtime_observation` 分开放。验收记录写明哈希不能证明两个历史时点的字节相同，实参也没有各自的词法区间。

因此，本阶段没有把差异提取假装成恶意更新检测。它也还没有差异提取。公平的后续实验不能把 p05.1 的 `verified` 当作检测真阳性，也不能把 `incomplete` 当作攻击类别。

`examples/evidence.json` 与当前函数输出一致，这是交付物锁定。样例文件哈希另由独立的 `hashlib.sha256` 计算核对，不完全依赖这份黄金文件。

## 9. 软件工程质量评价

`evidence.py` 只负责重放、绑定区间和索引。异常路径明确：图不合法、绑定路径不安全、绑定超过预算或 JSON 非法，都向外抛出；材料找不到则写入缺证。CLI 把前者映射为退出码 2，且不把缺证吞成退出码 0。

时间与空间随 P03 的条目和字节预算线性增长，另加一份不超过 256 KiB 的登记文件哈希预算。图和图内 SCS 以指针和哈希进入结果，不复制整份技能正文；witness 只保留主张片段或绑定对象文本。

绑定区间解析依赖“空白之后跳过一个逗号或括号”的游标。两项对象和不同键序的探针能够还原原对象。这个解析器比 `json.loads` 更依赖具体排版，但当前测试和探针没有打出错误区间。

缺证原因字符串过粗，见 P05-1。除此之外，模块边界清楚，没有为了通过测试而把失败改成空成功。

## 10. 现有测试有效性

`test_evidence.py` 有 12 个测试，本环境随全量 79 项一起通过。它们实际证明了：

- 样例哈希与双向包含关系，以及 `verified` 可以和 `partial` 同时存在
- 行重排后旧坐标失败，重新提取后按新坐标成功
- 文件表颠倒后，文件 witness 跟着新的数组位置，而不是跟着旧下标
- BOM 与 CRLF 的原始哈希、同一行两个 Unicode 调用的列号、次数不符时不分配
- 技能文件和分析者文件可以同时成为一条 `may_invoke` 边的来源；原件缺失时为 `partial`
- 伪造名称、伪造行号、改名后的旧路径、硬链接、`../` 路径、代码围栏改写
- 非法绑定抛错；CLI 的 0、1、2；黄金索引与当前函数一致

它们没有证明：目录中多出来的文件会被报告，超限文件的缺证原因与诊断一致，YAML 键序会被当成结构等价，以及符号链接逃逸。成功路径的 CLI 比较和黄金文件比较使用同一个 `build_index`。退出码、伪造主张和硬链接断言是独立的。这些测试不是只检查“没有抛异常”或“结果非空”。

## 13. 完整问题清单

### P05-1　文件缺证原因把预算截止和角色不符并成一句

- 严重等级：Minor
- 状态：CONFIRMED
- 文件：`src/dcfa/evidence.py` 180–183 行；`src/dcfa/skill_reader.py` 118–122 行
- 描述：登记文件大于 32 KiB 时，扫描诊断是 `inventory_hash_limit`，文件 witness 为空。原点上的 `missing_reason` 却是 `file_unavailable_or_role_mismatch`。角色实际上与清单一致，文件也存在。
- 根本原因：`file_witness` 只区分“有没有哈希”。没有哈希时统一使用同一个原因，再把声称路径放到 `claimed_path`。

- 验收：上述文件的 witness 仍为空，`missing_reason` 能单独表示预算截止，`mapping_status` 仍为 `incomplete`。

### P05-2　已验证索引不是快照文件清单
