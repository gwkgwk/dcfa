## 5. 核心算法正确性分析

论文摘要给出的链条是：抽象解释，构造对象数据流关系图（ODRG），把对象映射到信任域，提取跨域数据流，再比较两个版本的流集合。§4.2 用 import、属性读取、属性赋值和外部调用四类操作生成 owns 边与 data-flow 边。§4.3 从 `require` 根出发，分别沿 owns 和 data-flow 计算可达对象，得到跨域流集合。§4.4 计算新版本集合减去旧版本集合；空集视为良性更新，非空集标记为 rogue update。论文假设旧版本是良性的。

P07 没有重写这些步骤。文件模式调用的是上游函数。对已提交的顶层样例，本轮重新运行得到：

- 过滤前：旧版 572 节点、477 边；新版 836 节点、1377 边。
- `sanitize_and_export` 之后：旧版 0 节点、0 边；新版 233 节点、667 边。
- 旧版信任域为空。新版包含 `path` 和 `:local:demo.txt`。
- 新版关系为 `(:local:demo, path)`，附两条节点序列。
- `flagged_single_local_rels_from_tuples` 返回 `(:local, path)`。

这些数字与 `top-level/module-returns.json` 和本轮对 GraphML 的独立计数一致。旧版导出图是空的，因此这次“新增”是相对一个没有导出节点的旧图而言。报告把过滤前后的两套数字分开写了，没有混用。

见证序列不是只存在编号。新版导出图中：

- 节点 1713 是静态字符串，代码为 `demo.txt`，信任域为 `:local:demo.txt`。它有一条 `CONTRIBUTES_TO` 边指向 1762。
- 节点 1692 是 `require` 得到的对象，信任域为 `path`。它以 `basename` 连到 1741。
- 节点 1741 的名称是 `path.basename`，并有 `FUNC_OBJ_TO_RET_VAL` 边指向 1762。
- 节点 1762 是 API 返回对象。

因此记录中的两条序列，分别对应“本地字符串进入返回值”和“path 模块经 basename 进入返回值”。这与 §4.2 的外部调用数据流在方向上相符：参数和被调函数都影响结果。它仍是原始图上的一条局部证据，不是论文四类操作的逐条对照，也不是 §4.3 全部跨域流的闭包。

归一化后的 `(:local, path)` 去掉了 `demo`。报告写明关系名发生了变化。§4.4 的判定对象是完整的新流集合。这里只核对了一个原始函数的返回值。该函数对这段无害更新给出了非空结果；若把它直接当成 §4.4 的判定，这段更新会被标成 rogue update。报告没有做这个推断。

包对入口本轮再次打印两个包分析成功、随后警告 `No files processed`，再在 `rogue_one_runner.py` 第 322 行读取 Windows `psutil` 所没有的 `pmem.shared` 时抛出异常。没有原生结果文件。警告的具体文件选择原因，报告写明尚未定位；本轮也没有新的证据可以定位它。

`top-level.log` 中的 `Detection: failed` 与空的 `Vulnerable files` 属于 ODGen 风格的检测统计。域差分的证据在 JSON 返回值里。两者不能合成一次“检测成功”。
