## 5. 核心算法正确性分析

科学问题是：在不执行不可信 Skill 的前提下，一个 Python 入口的直线子集能否稳定地变成对象、所有权和可能数据流，并带回源码位置。设计没有把这个问题写成闭包公式，实现也没有计算闭包。因此正确性要分成两层：设计中的操作语义，以及被引用的论文边规则。

操作语义里，下面几项与代码和独立运行一致。

- 环境是名字到对象编号的映射。`a='old'; b=a; a='new'` 之后，`b` 仍指向旧字面量，`a` 指向新字面量。
- 本地调用每次构造新的参数字典。`pick` 的两次调用分别返回 `'new'` 和 `'other'`；`left.run` 返回参数，`right.run` 返回 `'no'`，二者不会合并。
- 返回值就是被返回的对象编号。`x=pick(...)` 的 definition 绑定指向 `'new'` 那个节点，不是一个新复制的结果。
- 外部调用把每个实参和被调对象连到新结果。`f.write(secret)` 有从 `'s'` 到域为 `file`、名为 `write` 的结果的 data-flow。
- 图是有向无环的：检查过的程序里，每条边的目标编号都大于源编号。对象只向前创建。
- `if`、语法错误、未绑定名字、关键字调用和星号实参都变成 `partial`，不会假装两边都执行，也不会把 Skill 文档里的句子当成指令。

与这套操作语义不符、或比论文对象图更弱的地方如下。

`from api import emit` 被接受为 `complete_in_subset`。输出里有名为 `emit`、域为 `import:api` 的 api 节点，调用仍有 data-flow，但没有模块节点，也没有 owns。同一成员写成 `import api; api.emit('v')` 时则有模块节点和 owns。设计把这两种写法都算“显式外部模块成员”，却只实现了第二种。

`domain` 不是由 owns 闭包算出来的。`obj` 在创建时写入一个字符串：字面量和函数默认 `local`，`open` 为 `file`，属性成员复制所有者的域，调用结果复制被调对象的域，外部导入写成 `import:` 加模块名。论文 §4.2(2) 要求属性检索同时添加 owns 和 data-flow；§4.2(4) 要求外部调用同时添加 data-flow 和从函数到结果的 owns，并把接收者当作参数。当前属性边只有 owns，调用边只有 data-flow，`f.read()` 不把句柄当作实参。

这条差异有直接后果。对 `import api; f=open('demo'); x=f.read(); api.emit(x)`，存在一条从文件域节点到 `import:api` 节点的 data-flow，所以现有测试通过。沿 data-flow 从字面量 `'demo'` 出发，到不了 `emit` 的结果。路径数据停在句柄上；句柄到 `read` 方法只有 owns。文件“内容”实际上是带有 `file` 标签的调用结果，不是从路径或句柄沿 data-flow 流过来的值。

因此，实现具备设计中的直线对象解释能力，不具备论文 §4.2 的完整 ODRG，也不具备 §4.3 的跨域流集合。报告写了“没有等价于原论文的精度保证”和“完整跨域闭包尚未验收”，这个总判断是诚实的，但没有写明路径字面量不可达。仅凭域标签不能宣称文件数据已经流到外部接口。

未调用函数、自由变量和同目录包还有固定边界。未调用函数的函数体不会被走查，状态仍可以是 `complete_in_subset`。函数体只看见参数，所以模块级导入的名字在函数里是 `unresolved_Name`；把 api 对象或文件句柄作为参数传入则可以成功。这符合报告里的“不捕获全局或闭包”，也符合设计里的“独立参数环境”。它会漏掉只写在未调用函数里的行为，但失败时状态是 `partial`，不是一条伪造的完整流。找不到 `helper.py` 时，即使旁边有 `helper/__init__.py`，`import helper` 仍是确定的 `import:helper`，状态为 `complete_in_subset`。报告已把“缺文件即外部声明”写成假设。输出里没有不确定性字段。

## 8. 能力流图专项分析

本阶段的图是对象图，不是 P04 的 SCS 能力图。节点种类有 `literal`、`function`、`module`、`api`、`file_handle`、`result`。编号是本次 `nodes` 的下标，不是跨版本身份。同一段文本的两次字面量不会合并；同名函数来自不同文件时也不会合并。未调用函数只有一个函数节点，函数体里的对象不会出现。

边只有 `owns` 和 `data_flow`。方向是从已存在对象指向新建对象。`import api; api.emit` 的 owns 从模块指向成员。调用的 data-flow 从实参和被调对象指向结果。没有控制流边、权限边或条件边。`if` 不产生带条件的边，而是终止解释。两个相邻调用不会在它们的实参之间加边。

信任边界没有单独的边类型。它被压进 `domain` 字符串。这个字符串可以和 owns 可达集不一致：`open` 函数到句柄只有 data-flow，没有 owns，但句柄的域已经是 `file`。一个节点也只能有一个域字符串，不能表示论文里对象同时属于多个 owns 集的情况。

循环不会留在图里。普通自递归因为函数名不在参数环境中而停止；通过参数把函数传回自己时，深度检查停止。两种情况都不会生成回边。

这些限制不是通过补虚假边掩盖的。问题是标签和边各说各的，后续若只看其中一种，会得到不同的流。

## 9. 跨版本语义对齐专项分析

不适用。设计写明没有跨版本比较。代码没有第二个版本参数，没有相似度、阈值、一对多匹配或重命名对齐。文件移动、等价重构和同名冲突消解都不能在本模块中验收，也不构成未完成项。

单快照里能观察到的相关事实只有：对象身份不等于名字；覆写后旧对象仍在；重复导入同一函数会再创建一个函数节点。这不能当作对齐算法。

## 10. 差分及风险归因专项分析

不适用。输出没有新增、删除、修改、保留，也没有 `NEW_RISK`、`RISK_ESCALATED`、`EXISTING_RISK`、`RISK_MITIGATED` 或对应的未知风险状态。`complete_in_subset` 和 `partial` 只描述这次解释是否在子集内走完，不是安全结论。

因此：新版本尚未比较；旧风险不会被重新归因；多出来的节点本身也不是恶意判断。P07 里那对无害 `path.basename` 的非空差分没有进入本模块。审查没有要求本阶段提前实现风险差分。

## 12. 前置模块累计误差分析

P08 实际依赖的前置模块只有 `skill_reader.scan`。它不调用 P03 的 `extract`、P04 的 `build_graph`、P05 的 `build_index`，也不读 P06 预言或 P07 产物。端到端样本是真实目录：写入 `SKILL.md` 和 `.py` 后调用 `analyze`，由 `scan` 读字节并解码，再做 AST 解释。不是手工塞入一份理想 SCS。

继承下来的行为：

- 没有 `SKILL.md` 时，`scan` 在读脚本前返回 `document_unavailable`。解释器再追加 `missing_or_unsupported_entry`，节点为空。程序流本身不使用文档正文，但入口被阅读器的快照契约挡住。
- `inventory_only` 被滤掉，所以旁边的 `.js` 不会阻断 Python 入口，其文本也不会进结果。
- 另一个 `.py` 超过 32 KiB 时产生 `byte_limit`。因为已经有诊断，入口完全不解释，即使入口文件本身合法。这是失败关闭，也会掩盖入口里本来可以形成的流。
- `scan` 对支持的文件会先交出一次空文本记录。解释器用后一次解码文本覆盖。成功样例里的字面量证明最终用的不是空文件。

阶段一源码没有被 P08 修改。P07 工作区改动与这次解释器无导入关系，不构成 P08 的补丁。P04/P05 的 `possible`、证据哈希和位置指针不会自动出现在 P08 输出里；后续不能假定它们还在。

## 13. 科研科学性评价

本阶段由“Python 绑定不能沿用 JavaScript require 模型”这个问题引出，先有一份很短的设计，再有解释器。合成程序是手工输入，不是按某个评价集的标签写出来的规则。代码里没有 Skill 名、样本编号或攻击字符串分支。`open` 是设计点名的文件操作，不是某个样本的特判。

报告没有把结果叫做恶意更新，也没有把 `complete_in_subset` 叫做安全。闭包和跨版本判定被明确推迟。这符合“风险不是恶意意图、静态边不是攻击已经发生”。

科学上的薄弱点是形式化不够，而且论文引用宽于算法。设计把 §4.2–§4.3 和自己的边规则放在一起，但没有写出流集合，实现又少了论文里的一半边。报告事后补充了自由变量、缺文件即外部声明，以及精度不等价。这些句子是必要的，却不在已经提交的设计里。若下一阶段直接引用“P08 已按 RogueOne 建图”，就会把适配说成复现。

没有使用冻结评价集，也没有读取工作区里的 `evaluation.ndjson`。本阶段不能支撑检测率、漏报率或“发现恶意更新”的论文结论。它只支持一个更窄的结论：在所测直线子集内，对象身份和一部分可能数据流可以被静态记录，并且失败不会被标成子集内完成。

## 14. 软件工程质量评价

模块边界清楚。一个 `Analyzer` 持有源码、节点、边、绑定和函数表；`analyze` 负责读取和状态；`__main__` 负责 JSON 和退出码。没有为了这一阶段去改 CLI 的子命令表，与设计中的 `-m` 入口一致。

数据类型是普通字典，没有独立模式。字段含义要靠报告推断：`status` 两种字符串、`kind` 六种、`role` 三种。函数定义和导入不进绑定表，和“定义绑定”这个词不完全对齐。

异常路径多数变成 `issues` 里的一条记录，然后 `Incomplete` 被接住。第一条分析错误之后的语句不会再产生诊断。读取错误发生在解释之前时，入口结果直接为空。`RecursionError` 有单独原因。没有把异常吞成 `complete_in_subset`。

规模由阅读器的 32 KiB/256 KiB 和解释器的 4096 个对象、24 层调用封住。对象上限探针返回 4096 个节点并给出 `object_limit`。时间开销在这些上限内可以接受。没有网络、子进程或 `exec`。不可信文本只进入 AST。

可维护性的主要成本是规则写在条件分支里，论文边、域标签和诊断原因没有一张与代码同步的表。这不是风格问题，它已经造成 from-import 和属性 data-flow 的歧义。

## 18. 缺陷清单

### P08-M01

- 严重等级：Major
- 证据状态：CONFIRMED
- 位置：`src/dcfa/program_flow.py:173-181`；对照 `80-88` 和 `docs/P08-design.md:5`
- 描述：`from module import name` 在同目录没有模块文件时创建 api 节点并完成分析，不创建模块节点，也不创建 owns。属性写法 `module.name` 会创建 owns。

## 22. 修复验收标准

- `from module import name` 与 `import module; module.name` 的模块节点、owns 和 data-flow 有各自的预期，不能只检查域字符串。
- `open('demo'); read; emit` 同时公布标签结果和 data-flow 可达结果。若仍不可达，文档必须把这句写成预期，而不是写成文件数据已经流出。
- 缺文件、同名包目录和属性导入三种输入可以区分。
- 未调用函数、自由变量 `open`、模块文档字符串、普通自递归和邻居大文件都有固定诊断。
- 新测试不能调用被测函数来生成自己的预期，也不能读取仓库外的评价标签。
- 修复后的实现、测试和报告处于同一提交；`python -m pytest -q` 与 `ruff check .` 在该提交上重跑。
- 修复不得给输出增加恶意、良性或跨版本风险状态。
